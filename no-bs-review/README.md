# 不废话代码审查（No-BS Review）

> 拒绝教条主义与过度设计，按务实而严格的工业级工程规范把关合并前代码质量。

---

## 💡 为什么需要这个技能？

市面上的大多数 AI Code Review 往往好心办坏事：
- **吹毛求疵**：报几十条无关紧要的变量名或语法糖建议，淹没真正致命的缺陷；
- **教条主义**：机械按照行数指标逼人拆分方法，导致状态传参复杂化、排障断点困难；
- **过度设计**：动辄建议套用策略模式、建造者模式、提取抽象层，徒增理解与维护成本；
- **好心添乱**：评审时擅自改写代码，破坏存量项目的既有设计与架构惯例。

**不废话代码审查**从一线资深工程师的工程实践出发，确立了唯一的裁决优先级链：

```text
正确 > 可读 > 可调试 > 项目一致 > 可维护 > 简洁 > 性能 > 优雅
```

> **核心原则**：代码首先写给人看，其次才是写给机器执行。简单不是低级，清晰本身就是高级工程能力。

## 🔍 四遍审查机制

1. **第一遍：🔴 红线（无条件必改，零容忍）**
   - if / for / try 嵌套超过 3 层
   - 匿名函数/闭包内再嵌匿名函数（含 Lambda）/ 嵌套三元表达式
   - 存量项目无理由新增第三方依赖
   - 边界未覆盖、并发隐患、异常路径丢失
   - 命中注入、越权、敏感泄露、反序列化等安全清单

2. **第二遍：🟡 黄线（触发思考，不是“必须拆”）**
   - 单方法 ~60 行、新建单文件 ~400 行、链式调用 ~5 环、泛型嵌套 2 层
   - **3句话自检**：能否用 3 句中文说清流程？说得清就保留现状，说不清才建议拆分。
   - **为凑数字而拆分本身就是违规**：100 行的扁平 switch 远好于 30 行的三层嵌套循环。

3. **第三遍：🛡️ 反过度设计**
   - 能用 switch 不造多态；能用 if/else 不搭策略模式；参数 ≤ 4 个不造 Builder
   - Spring 默认三层（Controller → Service → Mapper/Repository），拒绝凭空引入复杂分层
   - 增加抽象必须满足 5 个正当理由之一，绝不为“未来可能出现的变化”提前设计

4. **第四遍：🛠️ 语言与专项细则**
   - **全语言通用工程底座**：执行统一的红线、黄线与反过度设计标准，语言特有语法遵循该语言主流规范。
   - **Java 专属深度**：按单环复杂度评估 Stream，业务逻辑严禁埋入链式调用；Optional 不做强行包装；异常与日志保留完整现场。
   - **TypeScript / Vue 专属深度**：类型复杂度总判据“类型比业务难懂则降低复杂度，宁可 `as` 断言”；Vue 3 规范；检查未清理的监听器/定时器。
   - **后端安全与性能**：防范 SQL 注入、XSS、越权、路径穿越；杜绝循环查库（N+1）、无分页全量查询。

## 📋 结构化输出规范

每次审查输出固定、克制、可审阅的结论：

```markdown
## 审查结论：可合并 ｜ 修改后可合并 ｜ 需要重做
一句话说明整体判断。

### 🔴 必须修复（N 项）
1. `文件:行号` — 问题说明。
   - 依据：违反的规则 + 规则背后的真实工程原因
   - 建议：提供最小 Before/After 示例

### 🟡 建议关注（N 项）
（作者能说明充分理由的允许保留现状）

### 💡 顺带提示（最多 2 条）
只提紧邻修改点的明显小问题，严控噪音。

### 未检查项
如实列出本次未验证的项目（如未运行测试、未核实索引）。
```

## 🚀 触发方式

在 WorkBuddy 中发送如下内容即可自动激活：
- *“帮我 review 一下这段代码”*
- *“做下合并前的代码审查”*
- *“CR 一下这个 PR / 这个文件”*
- *“检查下代码质量”*

> ⚠️ **边界声明**：本技能**只评估、不改动代码**（除非明确要求修复），不用于开发新功能，不用于自动重构。
