# Java 审查细则

> 随主技能加载，仅在审查 Java 代码时读取。

## Stream

简单场景可用：每环一行以内、Lambda ≤ 3 行。

出现以下任一情况 → 🟡 建议改写为 for 循环：

- 多次 map / filter / flatMap 链
- Lambda 内含业务逻辑
- 需要观察中间值来调试
- 存在副作用

为什么：Stream 的价值在声明式表达简单变换。业务逻辑埋进链里，会丢失可断点性和可读性，而这两样在排查线上问题时比"写得短"重要得多。

链式调用真正的判据是单环复杂度：`.filter(o -> o.getStatus() == VALID)` 再多几环也无妨；某一环塞进 5 行 lambda，两环就该拆。

## Optional

只用于表达"返回值可能没有"。为了少写一次 null 判断而强行包装 → 🟡。

## record / Lombok

- record：版本支持且作为纯数据载体时可用；不要求批量改造现有 POJO。
- Builder：项目已用 Lombok `@Builder` 就跟随；参数 ≤ 4 个直接构造，手写 Builder → 🟡。

## 默认不用（出现即质疑）

sealed class、自定义泛型方法、自定义注解 + AOP 承载业务逻辑。这些理解成本高且几乎总有更朴素的等价写法。

## 隐式机制必须有注释

AOP 切面、注解驱动的业务行为、反射与动态代理、Spring 多实现装配（`@Primary` / `@Qualifier` / 条件装配）——这些机制读代码看不出会执行、断点断不到、出问题无从查起。没有中文注释说明 → 🟡。

## 异常处理

- 复用项目现有体系（`BusinessException` / `ServiceException` / `Result` / `ErrorCode`），自造异常层次 → 🟡
- 错误信息必须能定位问题：`订单不存在：orderId=12345` 合格；`参数错误` 不合格
- 吞异常、无意义的重新包装 → 🔴（丢掉现场属于正确性问题，不是风格问题）

## 日志

- 关键日志必须带上下文（订单号、用户 id、关键参数）
- 以下 → 🟡：循环内大量日志、重复日志、序列化整个对象、输出敏感信息（密码、token、身份证号）

## 测试（有测试时才审）

- 三步结构：输入 → 执行 → 结果
- 命名表达业务行为：`shouldReturnEmptyWhenOrderDoesNotExist`
- 测试代码同样遵守可读性原则，不为测试代码降低标准

## 注释规范

- 只注释 why（业务原因、特殊约束、外部系统限制、容易误解的地方）。复述代码语义的注释 → 💡 建议删除
- 公开方法有 Javadoc / 文档注释，参数与返回值写**业务含义**而非类型
- 关键副作用（改缓存、触发事件、发消息）必须显式说明，缺失 → 🟡
- TODO 带负责人与主题标签：`// TODO(负责人): 当前用轮询，后续改为事件驱动 #性能`；文件头署名、日期格式以团队现有约定为准，不要向陌生团队强加署名规则
- 大段注释掉的死代码 → 建议删除，历史交给 Git
